## 5.1 用户模块实现

### 5.1.1 注册与登录功能

#### 功能描述与实现思路

用户模块是系统的基础模块，负责用户的注册、登录、密码重置等核心功能。系统采用 Django REST Framework 提供的用户认证体系，结合 JWT（JSON Web Token）实现无状态认证。

**注册功能**：用户通过填写用户名、邮箱、密码和确认密码完成注册。后端对输入数据进行严格校验，包括用户名唯一性、邮箱唯一性、密码强度验证等。注册成功后，系统自动创建对应的 UserProfile 记录，用于存储用户的个性化配置。

**登录功能**：用户输入用户名和密码后，后端通过 Django 的 authenticate 方法验证凭据。验证通过后，生成 JWT Access Token 和 Refresh Token，并将用户信息（包含头像、API 密钥配置等）一并返回给前端。前端将 Token 存储在 localStorage 中，后续请求通过 Authorization 请求头携带 Token 进行身份验证。

**密码重置**：系统提供两种密码重置方式。正式环境通过邮件发送重置令牌，测试环境支持直接通过用户名或邮箱重置密码。重置令牌具有过期时间限制，确保安全性。

#### 关键代码片段

JWT Token 生成逻辑（后端 views.py）：

```python
refresh = RefreshToken.for_user(user)
# 合并用户信息和配置信息到同一层级
user_data = UserSerializer(user).data
profile_data = UserProfileSerializer(profile, context={'request': request}).data
user_data.update(profile_data)
return Response({
    'refresh': str(refresh),
    'access': str(refresh.access_token),
    'user': user_data
})
```

前端登录状态管理（auth.js）：

```javascript

user.value = responseData.user
localStorage.setItem('token', newToken)
localStorage.setItem('user', JSON.stringify(responseData.user))
service.defaults.headers.Authorization = `Bearer ${newToken}`
```

### 5.1.3 JWT 认证与密码安全

#### 功能描述与实现思路

系统采用 JWT（JSON Web Token）作为认证方案，相比传统的 Session 认证，JWT 具有无状态、跨域友好、适合分布式系统等优势。

**Token 机制**：系统使用 SimpleJWT 库实现 JWT 认证。用户登录后获得 Access Token（有效期 24 小时）和 Refresh Token（有效期更长）。Access Token 用于日常 API 请求的身份验证，Refresh Token 用于在 Access Token 过期后获取新的 Access Token，无需用户重新登录。

**密码安全**：密码使用 Django 内置的 PBKDF2 算法进行哈希存储，不保存明文密码。注册时通过 validate_password 进行密码强度校验，要求密码包含字母和数字，长度不少于 8 位。

**权限控制**：后端通过 DRF 的 permission_classes 装饰器实现接口级别的权限控制。公开接口（如登录、注册）使用 AllowAny，需要认证的接口使用 IsAuthenticated，管理员接口使用 IsAdminUser。

#### 关键代码片段

Token 刷新逻辑（auth.js）：

```javascript
const response = await service.post('/token/refresh/', {
    refresh: refreshToken
}, { timeout: 10000, _isRefreshRequest: true })
token.value = responseData.access
localStorage.setItem('token', responseData.access)
service.defaults.headers.Authorization = `Bearer ${responseData.access}`
```

### 5.2.2 消息收发与流式响应

#### 功能描述与实现思路

消息收发是系统的核心功能，支持用户发送文本消息并接收 AI 助手的流式响应。流式响应技术（SSE, Server-Sent Events）使 AI 的回答逐字显示，大幅提升用户体验。

**流式响应实现**：后端使用 Django 的 StreamingHttpResponse 返回 SSE 格式的数据流。前端使用 Fetch API 配合 ReadableStream 逐块读取响应内容，实时渲染到界面上。

**消息历史**：每次对话时，系统将该会话的历史消息（最多保留 8 条）作为上下文发送给 AI 模型，使 AI 能够理解对话上下文，提供连贯的回答。

**缓存机制**：对于相同的用户输入，系统优先从缓存中获取响应，减少 API 调用次数，提高响应速度并降低 API 费用。

#### 关键代码片段

## 5.3 模型管理模块实现

### 5.3.1 多模型适配器设计

#### 功能描述与实现思路

系统支持多种 AI 大模型，包括通义千问（Qwen）、OpenAI（GPT）、Google Gemini、月之暗面（Kimi）、深度求索（DeepSeek）、字节跳动（Doubao）等。为统一管理不同模型的 API 调用，系统采用适配器模式设计了多模型适配器架构。

**基类设计**：BaseAIApi 作为所有 AI API 的抽象基类，定义了统一的接口规范，包括消息发送、流式输出、配置验证等方法。各具体模型 API 类继承基类并实现各自的细节。

**适配器实现**：每个 AI 模型对应一个适配器类（如 OpenAIApi、QwenApi、GoogleGeminiApi 等），负责处理该模型特有的请求格式、响应解析、API 密钥获取等逻辑。

**增强包装器**：EnhancedApiWrapper 作为统一的 API 入口，根据模型名称自动创建对应的适配器实例，并处理 API 密钥检查、模型可用性判断、自动降级等高级功能。

## 5.6 关键问题与解决

### 5.6.1 跨域与 JWT 传递

#### 问题描述

前后端分离架构下，前端（Vite 开发服务器，端口 5173）与后端（Django 开发服务器，端口 8000）存在跨域问题。浏览器出于安全考虑，默认阻止跨域请求。同时，JWT Token 需要在每次请求中正确传递，确保身份认证的有效性。

#### 解决方案

**CORS 配置**：后端使用 django-cors-headers 中间件处理跨域请求。在 settings.py 中配置 CORS_ALLOWED_ORIGINS，允许前端域名访问。同时配置 CORS_ALLOW_CREDENTIALS=True，允许携带 Cookie 和认证信息。

**Vite 代理配置**：前端开发环境中，通过 Vite 的 proxy 配置将 /api 和 /media 路径的请求代理到后端服务器，避免浏览器跨域限制。代理配置包括 changeOrigin、超时设置、流式响应支持等。

**JWT 传递**：前端使用 Axios 拦截器，在每次请求的 Authorization 请求头中自动添加 Bearer Token。登录成功后，Token 存储在 localStorage 中，页面刷新后自动恢复。

#### 关键代码片段

Vite 代理配置（vite.config.js）：

```javascript
proxy: {
    '/api': {
        target: 'http://127.0.0.1:8000',
        changeOrigin: true,
        ws: true,
        timeout: 60000,
        buffer: false  // 支持流式响应
    },
    '/media': {
        target: 'http://127.0.0.1:8000',
        changeOrigin: true
    }
}
```

Axios 请求拦截器（request.js）：

```javascript
service.interceptors.request.use(config => {
    const token = localStorage.getItem('token')
    if (token) {
        config.headers.Authorization = `Bearer ${token}`
    }
    return config
})
```

### 5.6.2 流式响应中断处理

#### 问题描述

流式响应过程中，可能因网络波动、服务器超时、用户主动取消等原因导致响应中断。如果不妥善处理，会导致前端显示不完整的内容或卡死状态。

#### 解决方案

**多层降级机制**：系统设计了三层降级机制。第一层优先尝试流式响应；第二层在流式失败后尝试非流式响应；第三层在前两层都失败时返回模拟响应，确保用户始终能收到回复。

**前端超时处理**：前端设置合理的超时时间（60 秒），超时后自动终止请求并提示用户。同时提供"重新生成"按钮，允许用户重新发起请求。

**后端异常捕获**：后端在流式响应生成器中使用 try-except 捕获异常，确保即使发生错误也能返回完整的 SSE 结束信号，避免前端卡死。

**连接保活**：后端配置 X-Accel-Buffering: no 禁用 Nginx 缓冲，配置 Cache-Control: no-cache 确保流式数据实时推送。前端配置 keep-alive 保持连接活跃。
